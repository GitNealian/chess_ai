# 对手意图推演设计

日期：2026-09-22

## 目标

1. 在对手刚走完一步、轮到我方的局面，推演并展示对手后续连招，帮助练习棋感：
   - **底线威胁线**：若我方完全不理会（停一手），对手接下来 3~4 步的最佳连招及结局；
   - **圈套分支**（默认 2 条）：若我方走了某个「诱饵着法」（表面诱人实则中计，如贪吃、随手棋），对手的惩罚连招及结局；
   - **正着参考**：排名榜首着法，作为对照。
2. 结局统一量化：绝杀（步数）/ 白丢某子 / 终点红方视角分数。
3. **零侵入**：不影响现有引擎的搜索与评估行为、不影响现有 AI 分析（评分）链路的性能与输出。
4. 触发架构：意图与评分相互独立；前端**先请求意图（快），意图完成后再请求评分分析**，两者不并发。

## 现状

- 引擎（`backend/engine/`）：negaScout/PVS + 迭代加深，`search_depth(st, ctx, stack, depth)` 为公开入口；每次搜索后根着法排名缓冲 `ctx.root_moves` / `ctx.root_scores`（分数降序）保留在调用方创建的 `Ctx` 中，可直接读取。
- `analyze(fen, ...)` 生成器（`analysis.py`）逐层产出 `AnalysisResult`（score / mate / pv / nodes / time_ms），供 `/api/engine/analyze` NDJSON 流式接口使用；层边界软时限、停旗契约、Lazy SMP 并行均已就绪。
- 前端对弈页 / 打谱页已有自动评分链路：走子后调 `analyzeStream`，逐层更新评分条与一步推演箭头。
- 评估器具备子力、位置、机动性、攻防掩码维度；着法生成 / 中文记谱转换可复用。

## 方案选择

**方案（采纳）：底线威胁（null-move 推演）+ 诱饵分支惩罚推演，独立端点**

- A 线：构造「跳过一手」局面（翻转 side_to_move）搜索对手最佳连招，得到「完全不理会」的底线威胁。
- B 线：从着法排名中按启发式挑 2~3 个诱饵着法，逐个 make 后搜索对手惩罚线。
- 输出为着法序列 + 结局，不依赖外部服务，确定性可解释。

**方案（未采纳）：单一威胁线**。只有一条「完全不理会」的极端线，覆盖不了「贪吃中计」等常见菜鸟着法。

**方案（未采纳）：正确线 vs 圈套线对比**。圈套只有一条，探索感弱。

**方案（未采纳）：一次搜索两用（rank 事件兼作评分结果）**。迭代加深是一条连续流：评分需迭代到 16 层（最长 30s），而意图排名在 depth 6~8 即可出结果，深度语义不同，强行合并会互相等待或引入层间插桩（需复制 `analyze` 的并行/时限/停旗骨架，维护成本高）。

**方案（未采纳）：两请求并发触发**。意图全并行会与评分的 8 线程 Lazy SMP 争抢 CPU（20 核上叠加 16 线程），双方耗时上升、深度变浅；改为「先意图、后评分」串行后，评分启动时机器已空闲，性能与现状一致。

## 核心算法

```
局面 P（对手刚走完，轮我方）
 ├─ ① 着法排名：编排层自建 Ctx → search_depth（固定浅深度，默认 8，threads=1~2）
 │      → 读 ctx.root_moves / root_scores → 正着 + 诱饵候选
 ├─ ② A 线：FEN 字符串层翻转 side_to_move → load_position → 限时搜索
 │      → 对手最佳连招 3~4 步 + 结局
 └─ ③ B 线：每个诱饵 e → make(e) → 限时搜索对手惩罚线
        → 连招 + 结局；串行逐分支产出
```

- **诱饵筛选启发式**（最多 `max_baits`，默认 2）：
  - 吃子着法优先：吃到的子价值高（≥ 炮/马）且与最佳分差不大（如 ≤ 80 分）→「贪吃陷阱」；
  - 排名第 2~3 的非吃子着法 →「看似也行的随手棋」；
  - 候选不足时按实际数量产出。
- **结局判定**：将杀（`mate` 步数）/ 吃掉对方某子（对比吃子前后 `remain` 子力）/ 终点红方视角分。
- **边界情形**：
  - 我方正被将军：无法用合法着法表达「停一手」，A 线降级为提示「你正被将军，必须应将」，仅产出 B 线（诱饵从应将着法中挑）；
  - 「跳一手」后为「将帅可被吃」局面：实现时验证引擎对该局面的搜索行为（吃将 = 绝杀分）；不合法则同样降级为 B 线；
  - 排名搜索 / 任何子搜索被中断：丢弃该分支，已产出事件保留，正常收尾 `done`。

## 零侵入约束（硬性要求）

- 新逻辑全部落在**新文件** `backend/engine/intent.py`（编排层），只调用现有公开接口：`load_position` / `prepare` / `search_depth` / `analyze`；多分支各自限时、串行执行（threads=1~2），全程不启动辅助线程。
- 着法排名：编排层自建 `Ctx` → `search_depth` → 读 `ctx.root_moves` / `ctx.root_scores`，不改 `analysis.py` / `search.py`。
- 现有文件唯一改动：`backend/routes/engine.py` **新增** `/api/engine/intent` 端点（纯新增代码，不改已有函数）。
- **不改**：search / evaluate / movegen / position / bitboard / tables / eval_tables / zobrist / constants 等所有搜索评估模块；`fen.py` 也不改（跳一手只在 FEN 字符串层翻转 side_to_move 字段，复用现有 `load_position` 解析路径）。
- 验收：现有全部后端测试通过；`/api/engine/analyze` 输出行为不变（新增对照测试）。

## 触发架构

```
对手走子 → 前端发 POST /api/engine/intent（快：排名 <1s + 3~4 个限时小搜索，总 2~5s）
         → 意图事件全部到达、渲染意图卡片
         → 前端再发 POST /api/engine/analyze（现有评分链路，行为不变）
```

- 两者为独立请求、串行触发：意图搜索是浅层单线程小任务（占 1~2 核、2~5s），评分启动时机器空闲，无 CPU 争抢。
- 深度解耦：意图排名用固定浅深度（默认 8，可配），评分继续自身迭代加深（最高 16 层）。
- 取消语义：用户切着法 / 走子 / 悔棋时前端断开旧流，两个端点复用现有停旗契约，毫秒级停止。
- 取舍：两个独立 Ctx（约 80MB 置换表），单用户场景可接受；意图与评分重复的只是浅层搜索（总量 1~2s），换取完全解耦与零侵入。

## 后端接口设计

### `POST /api/engine/intent`

加在 engine 蓝本（`backend/routes/engine.py`），NDJSON 流式（`application/x-ndjson`），复用 analyze 端点的「线程 + 队列 + ping」流式模式。

请求：

```json
{
  "fen": "局面 FEN（与 initial_fen+moves+ply 二选一）",
  "initial_fen": "可选，缺省为初始局面",
  "moves": [{ "x1": 1, "y1": 2, "x2": 4, "y2": 2 }],
  "ply": 3,
  "time_limit_ms": 2000,
  "max_baits": 2
}
```

- `fen` 或 `initial_fen + moves + ply` 定位局面，语义与 `/api/engine/analyze` 一致；局面必须「轮到我方」（即对手刚走完），否则 400。
- `time_limit_ms`：每个子搜索的限时（默认 2000，范围 500–5000）；`max_baits`：诱饵分支上限（默认 2，范围 1–3）。

事件流（依次出现）：

```jsonc
// 着法排名（正着参考）
{"type":"rank", "best":{"x1":..,"y1":..,"x2":..,"y2":..,"chinese":"..","iccs":"..","score_red":..},
 "list":[ /* 前 k 个，含上同字段 */ ]}

// 底线威胁线；被将军时 line 为空数组并带 hint
{"type":"threat", "line":[{"x1":..,"y1":..,"x2":..,"y2":..,"chinese":"..","iccs":".."}],
 "outcome":{"mate":3, "loss_piece":null, "score_red":-1500}, "hint":null}
{"type":"threat", "line":[], "outcome":null, "hint":"你正被将军，必须应将"}

// 圈套分支（每条诱饵一个事件）
{"type":"bait",
 "bait":{"x1":..,"y1":..,"x2":..,"y2":..,"chinese":"车二进五","iccs":"h2e2","reason":"贪吃"},
 "line":[ /* 对手惩罚连招 3~4 步 */ ],
 "outcome":{"mate":null, "loss_piece":"车", "score_red":-950}}

// 结束 / 错误（与 analyze 语义一致）
{"type":"done", "time_ms":3200}
{"type":"error", "message":".."}
{"type":"ping", "elapsed_ms":..}
```

- `outcome.mate`：将杀 ply 数（正数表示我方被绝杀）；`outcome.loss_piece`：该线终点我方损失的最大子力角色名；`outcome.score_red`：该线终点的红方视角引擎分（前端可量化损失、排序）。
- 事件产出顺序：`rank` → `threat` → 各 `bait` → `done`；任一子搜索失败不中断整流（跳过该分支继续）。

## 前端展示

- 对弈页 / 打谱页 AI 分析区新增「对手意图」卡片（复用现有记谱渲染样式）：
  - 「若不理会：车8进1 → 车8平7 → **绝杀**」（threat）；
  - 「若你走 车二进五（贪吃）→ 炮8平3！→ 车8进9，白丢一车」（各 bait，`reason` 标注诱饵类型）；
  - 「正着参考：士四进五」（rank.best）。
- 触发：走子 / 切着法 / 悔棋后**先发意图请求**，意图流 `done` 后再走现有评分分析请求；旧流未完成时先断开再发新流。
- 状态管理：play 会话 store 与打谱 practice store 各加 intent 状态位（加载中 / 数据 / 错误静默降级——意图失败不影响评分分析）。

## 测试策略

- **引擎层**（`backend/tests/`）：
  - 跳一手 FEN 构造：普通局面翻转正确；我方被将军时正确降级；
  - 诱饵筛选启发式：构造「贪吃陷阱」局面（吃炮必中伏）断言选中该吃子着法；无合适诱饵时产出数正确；
  - 威胁线 / 惩罚线结局判定：已知绝杀局面断言 `mate`；已知失子局面断言 `loss_piece`；
  - 排名读取：`search_depth` 后 `ctx.root_moves` 排序与 `root_scores` 单调性。
- **API 层**：NDJSON 事件序列与字段快照（`threads=1` + 固定深度，规避 Lazy SMP 非确定性）；非法参数 400；中断（客户端断开）后服务端停止。
- **回归验收**：现有全部后端测试通过；`/api/engine/analyze` 输出行为不变（对照测试）。
- **前端**：意图卡片渲染、触发顺序（意图 done 后才发评分请求）、旧流取消。

## 已知取舍与限制

- 意图推演基于浅层搜索（排名 depth 8、威胁/惩罚线限时 2s），线路深度与精度有限；对手「最佳连招」仅在该深度下成立。
- 诱饵筛选是启发式，可能漏掉某些人类易犯错误、也可能选出不典型的诱饵；`max_baits` 可调。
- 「跳一手」局面与真实对局不同（对手等于多走一步），威胁线结论仅在「我方完全不作为」前提下成立，前端文案需明示该前提。
- 并行关闭（threads=1~2）下浅搜索足够快，但 Lazy SMP 非确定性带来的同局面结果微变在意图场景同样存在（线路可能 ±1 步差异）。
- 打谱页历史着法逐个查看时，每次都会触发意图请求；靠前端取消旧流 + 浅搜索低耗时控制总量，不做服务端缓存（单用户规模收益小）。
